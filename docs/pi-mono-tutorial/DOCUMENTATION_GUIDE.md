# 系列文档编写指南

> 基于 pi-ai 系列文档编写经验总结

本文档总结了编写技术系列文档的最佳实践和经验教训，用于指导后续系列章节的文档编写。

---

## 一、前期准备阶段

### 1.1 代码分析优先原则

**必须通读实际代码**，不能仅依赖现有文档或外部资料。

#### 分析清单
- [ ] 通读核心源码文件
- [ ] 对比"教程描述"与"实际实现"的差异
- [ ] 识别被简化或遗漏的关键细节
- [ ] 理解设计决策背后的原因

#### 我们的实际发现（pi-ai 案例）

| 原教程描述 | 实际实现 | 差异说明 |
|-----------|---------|---------|
| "provider/model" 格式 | `Model` 对象，包含完整元数据 | 原描述过于简化 |
| 简单的 `AsyncGenerator` | `AssistantMessageEventStream` 类 | 实际是双向流控制 |
| 未提及延迟加载 | `createLazyStream` 是关键设计 | 遗漏了核心机制 |
| 基础类型定义 | 复杂的泛型约束和条件类型 | 类型系统被低估 |

### 1.2 架构理解分层法

```
第一层：整体架构（鸟瞰图）
    ↓
第二层：模块设计（组件关系）
    ↓
第三层：实现细节（代码层面）
    ↓
第四层：使用模式（实际应用）
```

**建议工具：**
- `read` - 读取核心文件
- `grep` - 搜索特定模式
- `glob` - 查找文件结构
- `task` - 并行分析多个模块

## 二、内容设计原则

### 2.1 渐进式难度设计

每个系列都应包含清晰的难度分级：

| 级别 | 目标读者 | 内容特点 | 代码复杂度 |
|-----|---------|---------|-----------|
| **入门** | 初学者 | 概念为主，建立整体认知 | 简单示例 |
| **进阶** | 有基础者 | 原理+实现，深入理解 | 完整实现 |
| **专家** | 高级开发者 | 生产级实践，最佳模式 | 生产代码 |
| **参考** | 所有开发者 | 完整API，快速查阅 | 片段示例 |

### 2.2 每章必备元素清单

```markdown
✅ 元信息
   - 难度标识（入门/进阶/专家/参考）
   - 预计阅读时间
   - 前置知识要求

✅ 内容结构
   - 问题引入（为什么需要这个？）
   - 架构图/流程图（可视化理解）
   - 核心代码实现（带详细注释）
   - 使用示例（可运行的代码）
   - 最佳实践（经验教训）
   - 总结（核心要点回顾）
   - 下篇预告（承上启下）
```

### 2.3 代码示例设计标准

#### ✅ 好的示例特征

```typescript
// 1. 完整且可运行
async function productionExample() {
  // 2. 有实际应用场景
  const context: Context = { messages: [] };
  
  // 3. 包含错误处理
  try {
    const response = await complete(model, context);
    // 4. 有详细中文注释
    // 处理响应...
  } catch (error) {
    // 错误恢复...
  }
}

// 5. 从简单到复杂递进
// 基础用法 → 进阶用法 → 生产级用法
```

#### ❌ 避免的示例问题

```typescript
// 过于简单，无实际意义
const model = getModel("openai", "gpt-4o");
const response = await complete(model, context);

// 缺少错误处理
// 无应用场景
// 无注释说明
```

## 三、技术内容编写技巧

### 3.1 复杂概念的讲解方法

采用**四层递进法**：

```
第一层：直观理解
├── 类比生活场景
├── 架构图示
└── 核心思想一句话总结

第二层：核心机制
├── 关键设计决策
├── 核心数据结构
└── 关键算法/流程

第三层：实现细节
├── 完整代码实现
├── 逐行代码注释
└── 边界情况处理

第四层：使用模式
├── 常见使用场景
├── 最佳实践
└── 性能优化建议
```

### 3.2 类型系统的文档化

**关键：展示类型如何保障安全**

```typescript
// 展示编译时检查
const openaiModel = getModel("openai", "gpt-4o-mini");
// 类型: Model<"openai-responses">

// ✅ 正确的选项
stream(openaiModel, context, {
  reasoningEffort: "high",  // OK: OpenAI 支持
});

// ❌ 错误的选项（会被 TypeScript 捕获）
stream(openaiModel, context, {
  thinkingEnabled: true,    // Error: OpenAI 不支持此选项
});
```

### 3.3 错误处理的完整覆盖

必须包含：
- [ ] 错误类型分类（网络/API/用户/内部）
- [ ] 错误事件 vs 抛出异常的对比
- [ ] 恢复机制和继续对话
- [ ] 调试方法和工具
- [ ] 生产环境的错误处理策略

## 六、系列文档规划

### 6.1 每个系列的必备组件

```
series-name/
├── README.md              # 系列入口和导航
├── 01-xxx.md             # 第一章
├── 02-xxx.md             # 第二章
├── ...
├── 09-api-reference.md   # API 参考（可选）
└── examples/             # 示例代码目录
    ├── basic/
    ├── advanced/
    └── production/
```

```markdown

- 在 README 中明确前置知识要求

- 交叉引用相关章节（"详见 02-xxx.md"）
- 保持术语和代码风格的一致性

## 七、常见陷阱与避免方法

### 7.1 过度简化

```markdown
❌ 错误示例：
"stream() 函数返回一个异步生成器"

✅ 正确示例：
"stream() 函数返回 AssistantMessageEventStream 实例，
它实现了 AsyncIterable 接口，支持双向流控制
（生产者 push 事件，消费者 for await 迭代）"
```

### 7.2 遗漏关键细节

```markdown
❌ 遗漏示例：
未提及延迟加载机制

✅ 完整示例：
详细讲解 createLazyStream 实现，包括：
- 为什么需要延迟加载
- 如何实现按需加载
- 错误隔离机制
- 性能优势
```

### 7.3 脱离实际

```markdown
❌ 脱离实际：
示例代码过于简单，无法用于生产环境

✅ 贴近实际：
提供生产级的完整示例，包括：
- 错误处理
- 超时控制
- 重试机制
- 日志记录
```

### 7.4 缺乏可视化

```markdown
❌ 纯文本：
仅用文字描述架构

✅ 可视化：
- 架构层次图
- 数据流图
- 时序图
- 对比表格
```

## 八、工具使用建议

### 8.1 代码分析工具链

```bash
# 1. 了解文件结构
glob "packages/xxx/src/**/*.ts"

# 2. 查找关键函数
grep "function stream" packages/xxx/src

# 3. 阅读核心文件
read packages/xxx/src/stream.ts

# 4. 并行分析多个模块
task(category="deep", prompt="分析 xxx 模块")

## 九、成功要素总结

### 9.1 核心要素（必须有）

1. **深入理解源码**
   - 不能只看表面
   - 理解设计决策
   - 识别关键细节

2. **分层渐进讲解**
   - 由浅入深
   - 循序渐进
   - 避免跳跃

3. **大量代码示例**
   - 理论与实践结合
   - 从简单到复杂
   - 生产级质量

### 9.2 增强要素（应该有）

4. **可视化辅助**
   - 架构图
   - 流程图
   - 对比表

5. **最佳实践**
   - 经验教训
   - 常见错误
   - 优化建议

6. **完整参考**
   - API 文档
   - 类型定义
   - 快速查阅

### 9.3 质量要素（必须有）

- 代码可运行
- 类型准确
- 链接有效
- 格式统一
- 无错别字
